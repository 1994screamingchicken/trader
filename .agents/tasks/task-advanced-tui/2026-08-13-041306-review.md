# FTXUI real-time trading dashboard

Adds a full-screen terminal UI to the Kraken Lua Trader, activated via `--tui`. The TUI renders live prices, script status, P&L, rate limiter stats, risk manager state, and recent log output in a multi-panel FTXUI layout. The existing text-based main loop is preserved as the default. A background thread ticks scripts and polls the WebSocket at the configured interval while FTXUI renders at ~4Hz. Watch for: use-after-move on `price_rows` that silently empties the live prices panel (confirmed), Ctrl+C signal not calling `screen.Exit()` so the TUI may hang until the next keypress (confirmed), and a double-mutex lock pattern in the ring-buffer sink that could deadlock under high log throughput (likely).

**Verdict**: NEEDS_CHANGES

## High-level view

The TUI replaces the main loop when `--tui` is passed: a background thread handles WebSocket polling and script ticking while FTXUI's `ScreenInteractive::Fullscreen()` renders the dashboard at 4Hz. The existing components — ScriptManager, RateLimiter, RiskManager — are all internally mutex-protected, making cross-thread reads from the renderer safe.

The `price_rows` vector is moved into a `prices_panel` that is then discarded, and the layout later references the now-empty `price_rows` directly. The "Live Prices" panel will always render empty.

Signal handling doesn't close the FTXUI event loop. The signal handler sets `g_running = false`, which terminates the background threads but doesn't call `screen.Exit()`. The TUI may hang until the user presses another key after Ctrl+C.

The ring-buffer log sink uses `base_sink<std::mutex>` (which locks the base-class mutex on every `log()` call) plus a separate `buffer_mutex_` inside `sink_it_`. Two mutexes locked in sequence on every log line is unnecessary and creates a subtle ordering hazard.

## price_rows use-after-move

Line 149 constructs `prices_panel`:

```cpp
auto prices_panel = vbox(std::move(price_rows)) | border | flex;
```

Line 299 in the layout composition:

```cpp
auto left_column = vbox({
    window(text(" Live Prices "), vbox(price_rows)) | flex_shrink,
    ...
});
```

After the move, `price_rows` is in a valid-but-unspecified state (in practice, empty). The Live Prices window will always render empty, and `prices_panel` — which holds the actual price elements — is never used anywhere. The fix is to replace `vbox(price_rows)` on line 299 with `prices_panel`, or remove the intermediate move entirely and build the panel inline in the layout.

## Ctrl+C / signal shutdown path

The signal handler sets `g_running = false`. The background threads check this flag and exit, which means they stop posting `Event::Custom` to the screen. The FTXUI main loop (`screen.Loop(component)`) then blocks on its internal file-descriptor read, waiting for the next terminal event. On Linux, SIGINT typically causes the read syscall to return EINTR, but FTXUI's loop retries the read rather than treating EINTR as an exit signal. Result: after Ctrl+C, the TUI appears frozen until the user presses any key.

The idiomatic fix is to post `screen.Exit()` from one of the background threads just before it terminates:

```cpp
// At the end of bg_thread or refresh_thread, after exiting the while loop:
screen.Post([&] { screen.Exit(); });
```

This wakes the event loop and causes `screen.Loop()` to return.

## Double mutex in RingBufferSink

`RingBufferSinkT<std::mutex>` inherits from `base_sink<std::mutex>`, which holds a mutex and locks it around every call to `sink_it_`. Inside `sink_it_`, the code acquires a second mutex (`buffer_mutex_`). Two mutexes locked in A→B order (base mutex → buffer_mutex_) on writes, but `get_messages()` only locks B. This isn't a classic ABBA deadlock, but it's an unusual pattern that:

- Adds unnecessary contention (every log message acquires two mutexes)
- Makes the locking protocol fragile if future changes introduce a path that acquires B→A

The cleanest fix: instantiate as `RingBufferSinkT<spdlog::details::null_mutex>` (which makes the base class lock-free) and rely solely on `buffer_mutex_` for thread safety. Or: keep the base-class mutex and remove `buffer_mutex_` from `sink_it_`, keeping it only in `get_messages()` / `clear()` / `size()` — the base mutex guarantees only one writer enters `sink_it_` at a time, so the deque is safe without a second lock on writes.

## Missing emergency-stop reaction in TUI mode

The classic main loop breaks on `g_emergency`:

```cpp
if (g_emergency) {
    logger->critical("Emergency stop triggered - shutting down");
    break;
}
```

The TUI's background thread has no equivalent check. When `RiskManager` triggers an emergency (via the callback that sets `g_emergency`), the scripts are halted by `ScriptManager::emergency_stop()`, but the TUI continues running indefinitely. The background thread should check `g_emergency` and call `stop()` + `screen.Post([&]{ screen.Exit(); })`.
