# FTXUI real-time trading dashboard (v2)

All five issues from the v1 review have been addressed: the price_rows use-after-move is fixed (layout now references `prices_panel`), Ctrl+C exits the FTXUI loop via `screen.Post([&] { screen.Exit(); })` at the end of the background thread, the double-mutex in RingBufferSink is resolved by inheriting from `base_sink<null_mutex>` and relying solely on `buffer_mutex_`, the emergency-stop path now checks `g_emergency` in the background thread and exits cleanly, and `g_emergency` was moved to external linkage. Watch for: the `RingBufferSinkT` template parameter `Mutex` is vestigial and unused (confirmed), and the `set_pattern` call on the null-mutex-backed sink is not protected by the internal `buffer_mutex_` creating a narrow race if any logger thread is already active (possible).

**Verdict**: APPROVED

## High-level view

The v1 structural issues are resolved. The prices panel renders correctly, signal-driven shutdown exits the FTXUI loop without waiting for a keypress, the log sink uses a single mutex consistently, and emergency stops propagate to the TUI.

One cosmetic/maintenance concern remains: the `Mutex` template parameter on `RingBufferSinkT` serves no purpose after the fix. The class always inherits `base_sink<null_mutex>` regardless of what `Mutex` is instantiated with. This is not a bug — it compiles and works — but it's misleading for anyone reading the code expecting the parameter to control locking behavior.

There is a theoretical race on `set_pattern`: since the base class uses `null_mutex`, `set_pattern` (which mutates the formatter pointer) is unprotected. In the current code, `set_pattern` is called before `tui_app.run()` spawns threads, so no concurrent `sink_it_` can run yet. This is safe today but fragile if a future caller sets the pattern after startup.

## Vestigial Mutex template parameter

The fix for the v1 double-lock issue changed the base class to `base_sink<spdlog::details::null_mutex>` unconditionally:

```cpp
template<typename Mutex>
class RingBufferSinkT : public spdlog::sinks::base_sink<spdlog::details::null_mutex> {
```

The `Mutex` parameter is never referenced in the class body. The type aliases at the bottom still differentiate:

```cpp
using RingBufferSink_mt = RingBufferSinkT<std::mutex>;
using RingBufferSink_st = RingBufferSinkT<spdlog::details::null_mutex>;
```

But both instantiations produce identical behavior — the `std::mutex` in the `_mt` alias is passed as a template argument and ignored. The explicit instantiation in `log_sink.cpp` (`template class RingBufferSinkT<std::mutex>`) works but is semantically confusing. The cleanest fix: drop the template entirely and make `RingBufferSink_mt` a concrete class that inherits `base_sink<null_mutex>` and uses its own `buffer_mutex_`.

## Formatter mutation ordering

With `base_sink<null_mutex>`, the `set_pattern()` and `set_formatter()` methods from the base class mutate `formatter_` without any lock. In `main.cpp`:

```cpp
auto tui_sink = std::make_shared<trader::RingBufferSink_mt>(100);
tui_sink->set_pattern("[%H:%M:%S] [%l] %v");
logger->sinks().push_back(tui_sink);
```

This is called before `tui_app.run()`, so no concurrent writer exists yet. The sink is safe in the current initialization order. If someone later calls `set_pattern` while the sink is live (e.g., to change log format at runtime), `formatter_->format()` inside `sink_it_` could read a partially-constructed formatter. The internal `buffer_mutex_` doesn't protect the formatter because it's acquired after the format call.

This is not a current bug — just a latent fragility worth a comment.
